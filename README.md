# 地图收藏迁移：点位偏移的根因与幂等修复法

> 把 A 地图的收藏夹搬到 B 地图，落点却总是偏几十米。本仓库记录一次完整的根因排查、判据设计，以及一套能长时间稳定跑完的抗限流批处理方案。

本仓库是**方法论文档**，不含任何个人数据与账号信息。所有结论都来自可复现的对照实验，文中标注了每项结论的验证方式。

---

## 一、它解决什么问题

跨地图平台迁移收藏时，最常见的做法是"拿到源平台的经纬度，直接写进目标平台"。这条路会稳定地偏。

**实测结论：同一个目标平台 POI，内部存在 4 套不同的坐标；只有其中一套是"这个门店真正的位置"。**

| 坐标来源 | 与"正确落点"的距离 |
|---|---|
| 搜索接口返回的主点 | 约 63 m |
| 搜索接口返回的入口点 | 约 115 m |
| **门店详情页点"收藏"按钮写入的点** | **0 m（正确）** |
| 用接口显式传坐标写入后实际存储的点 | 约 114 m |

四个值两两最大相差约 130 m。用第四种方式批量写入，就是偏移的来源。

---

## 二、判据：怎么判断一个落点到底偏没偏

不要拿"源平台的坐标"当基准 —— 两个平台的收录点位本来就不同，那不是错误。

**唯一可靠的判据是幂等性测试：**

```
对同一目标条目执行：取消收藏 → 重新收藏 → 比较前后坐标
```

| 结果 | 含义 |
|---|---|
| 变化 ≈ 0 m | 之前的落点本来就是对的（幂等） |
| 变化 ≈ 90–100 m | 之前的落点是错的 |

这个判据的好处：不依赖任何外部数据源，目标平台自己就是裁判。

**按写入批次抽样实测的结果（每批 5 条）：**

| 批次 | 平均变化 | 判定 |
|---|---|---|
| 早期「显式传坐标」写入 | 89 – 102 m | 系统性偏移，5/5 命中 |
| 后期「走详情页按钮」写入 | 20 m（4/5 恰好 0 m） | 已正确 |

两组的分离非常干净：**偏移不是坐标系问题，是写入路径问题。**

## 三、正确路径

```
按 poiid 打开门店详情页
        ↓
等待详情页操作栏渲染出「收藏」按钮
        ↓
点它
```

要点：

1. **不传任何坐标。** 由目标平台自己决定这个门店存哪套坐标。
2. **幂等。** 对已经正确的条目重复执行，坐标 0 m 不变 —— 因此可以安全地对全量数据重跑一次修复，不用先判断哪些是坏的。
3. **`poiid` 是关键。** 收藏记录本身自带 POI 标识，因此取消和收藏都不需要走搜索接口。整条链路可以做到**零搜索请求**。

## 四、几个必须踩过的坑

### 4.1 先删后写 = 数据丢失

最初的实现顺序是"先删除 → 再打开详情页 → 点收藏"。在约 20 秒/条的节奏下，单页应用会偶发初始化失败，结果是**点被删掉了但没被加回来**。

**修正：把顺序反过来 —— 先确认详情页可用，再执行删除。** 页面不可用就什么都不做，只记一条待重试。这样在结构上就不可能产生"删了加不回"。

### 4.2 把"查无此 POI"误判成限流

目标平台在找不到 POI 时，会返回一个固定的错误响应（响应体长度恒定、关键词字段被清空、`code` 为 `7`）。这**不是限流**。

真限流的表现是**请求挂起/超时**。两者必须分开处理：前者直接判定"平台无此 POI"，后者才退避重试。

曾经把前者当成后者做指数退避，最长空转了 1.5 小时。**诊断时空结果必须打印关键词、请求状态码、响应体长度和前 200 字符。**

### 4.3 强烈依赖带哈希的 CSS 类名

前端构建一变，写死的类名就全部失效，而且失败表现是"页面上找不到按钮"，很容易误判为账号被限。

**修正：改用 `[class*="前缀"]` 属性选择器 + 等待选择器出现 + 失败自动重新加载重试。**

## 五、稳定跑完的工程设计

目标平台的访问频率是有上限的。要长时间无人值守跑完，需要把"抗限流"做成结构性能力，而不是靠调参数。

| 机制 | 作用 |
|---|---|
| **滑动窗口配额** | 1 小时内请求数硬上限（本次取 300），超出自动等待窗口滑出 |
| **最小请求间隔** | 任意两次请求之间强制间隔，避免突发 |
| **两级熔断** | 接口连续失败 → 冷却 30 分钟；页面连续失败 → 冷却 10 分钟 |
| **探活恢复** | 冷却后先探测接口可用性，通过才继续；多次失败则安全退出而非硬刚 |
| **异常识别** | 状态码异常 / 返回非 JSON / 业务状态位异常 三类信号分别识别 |
| **失败补回队列** | 任何"已删除但未加回"的条目进入补回队列，收尾统一重试 |
| **断点续跑** | 每处理一条即落盘，按 POI 标识去重，中断后可原地继续 |

**节奏参考：** 300 请求/小时 ≈ 120 条/小时。慢，但可以整夜无人值守。

## 七、参考实现骨架

以下为流程骨架，用于说明顺序与状态机，不是可直接运行的成品。

```
读取收藏列表（含 POI 标识与坐标）
按写入时间分组，锁定需要修复的批次

for 每一条待修条目:
    # 阶段一：只读，不产生副作用
    打开门店详情页
    等待操作栏出现「收藏」/「已收藏」
    若超时 → 重新加载最多 3 次
    若仍失败 → 记录 page_unavailable，跳过（不删除任何东西）

    # 阶段二：确认页面可用后才写
    取消收藏
    复查按钮是否已变为「收藏」（若仍为「已收藏」→ 取消未生效，放弃本条，不点击）
    点击「收藏」
    回读校验：条目已入库，且坐标变化符合预期

    每条落盘；按 POI 标识去重以便续跑

收尾：对「已删除但未加回」的条目统一补回
```

**节奏控制**内嵌在请求层，而不是散落在业务代码里：所有出网调用统一走一个网关，由网关负责配额、间隔、熔断与计数。

## 八、适用边界

**适用：**

- 需要把收藏从平台 A 迁移到平台 B，且要求落点与平台 B 自己的门店点位一致
- 平台上存在"接口写入"和"页面按钮写入"两条路径，且两者结果不同
- 需要长时间无人值守跑完大批量写入

**不适用 / 需要额外处理：**

- 目标平台对收藏总量有硬上限。达到上限后继续写入会挤出最早的数据，**且接口返回的总数不会变化** —— 计数无法用来判断真实容量，必须依赖客户端界面确认。
- 纯行政区划名称（县、市、区）通过 POI 检索接口通常查不到，需要在地图上人工处理。
- 大型景区、山脉、湖泊等面状地理实体，其在两个平台的代表点天然相差数公里，不适用"偏移"判定，应按平台自身点位处理。
