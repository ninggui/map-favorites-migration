# 地图收藏迁移与批量写入：点位偏移的根因 + 批量写入的纪律

> 把 A 地图的收藏夹搬到 B 地图，落点却总是偏几十米；或者按一份外部清单在 B 地图批量收藏，跑得很快却收进来一堆错的。本仓库记录完整的根因排查、判据设计，以及一套能长时间稳定跑完、且不污染收藏夹的批处理方案。

本仓库是**方法论文档**，不含任何个人数据、账号信息、真实店名与坐标。所有结论都来自可复现的对照实验与真实跑批，文中标注了每项结论的来源与验证方式。

## 一、它解决什么问题

跨地图平台迁移收藏时，最常见的做法是"拿到源平台的经纬度，直接写进目标平台"。这条路会稳定地偏。

**实测结论：同一个目标平台 POI，内部存在 4 套不同的坐标；只有其中一套是"这个门店真正的位置"。**

| 坐标来源 | 与"正确落点"的距离 |
|---|---|
| 搜索接口返回的主点 | 约 63 m |
| 搜索接口返回的入口点 | 约 115 m |
| **门店详情页点"收藏"按钮写入的点** | **0 m（正确）** |
| 用接口显式传坐标写入后实际存储的点 | 约 114 m |

四个值两两最大相差约 130 m。用第四种方式批量写入，就是偏移的来源。

**第二个问题：批量写入不只是"落点准不准"。** 当输入是一份外部清单（例如从视频、图片里 OCR 出来的店名）时，真正的质量风险变成三件事——点错了行、名字对不上也收、把失败当成成功计数。这三件事在下面第四、五、六节逐条给出纪律。

## 二、判据：怎么判断一个落点到底偏没偏

不要拿"源平台的坐标"当基准 —— 两个平台的收录点位本来就不同，那不是错误。

**唯一可靠的判据是幂等性测试：**

```
对同一目标条目执行：取消收藏 → 重新收藏 → 比较前后坐标
```

| 结果 | 含义 |
|---|---|
| 变化 ≈ 0 m | 之前的落点本来就是对的（幂等） |
| 变化 ≈ 90–100 m | 之前的落点是错的 |

这个判据的好处：不依赖任何外部数据源，目标平台自己就是裁判。

**按写入批次抽样实测的结果（每批 5 条）：**

| 批次 | 平均变化 | 判定 |
|---|---|---|
| 早期「显式传坐标」写入 | 89 – 102 m | 系统性偏移，5/5 命中 |
| 后期「走详情页按钮」写入 | 20 m（4/5 恰好 0 m） | 已正确 |

两组的分离非常干净：**偏移不是坐标系问题，是写入路径问题。**

## 三、正确路径

```
按 poiid 打开门店详情页
        ↓
等待详情页操作栏渲染出「收藏」按钮
        ↓
点它
```

要点：

1. **不传任何坐标。** 由目标平台自己决定这个门店存哪套坐标。
2. **幂等。** 对已经正确的条目重复执行，坐标 0 m 不变 —— 因此可以安全地对全量数据重跑一次修复，不用先判断哪些是坏的。
3. **`poiid` 是关键。** 收藏记录本身自带 POI 标识，因此取消和收藏都不需要走搜索接口。整条链路可以做到**零搜索请求**。

**撤销（取消收藏）走的是另一条路，标识也不通用。**

搜索页列表项上那个标识，与收藏记录里的标识**不同源**。结果就是在搜索页看这条门店仍然显示"加入收藏夹"，从搜索页根本撤销不了——这一条曾让"撤销"卡了很久，误以为是没有权限。

正确路径是**收藏夹面板**：

```
打开收藏夹面板
        ↓
按收藏记录自己的标识定位到那一行
        ↓
先 hover 使操作区出现（删除控件默认不渲染/不可点）
        ↓
点删除 → 处理二次确认弹窗
        ↓
回读该行是否已消失；收尾再用账号侧计数复核
```

要点：

- 面板里每一行都带一个 `data-sid`，**它就是收藏记录的标识**，可以直接用来精确选行，不需要靠名称模糊匹配。
- 删除控件**默认不可见**，必须先 hover 那一行再点，否则点击会被静默忽略（既不报错也没有网络请求）。
- 与写入一致：**一次只删一条、按标识定位**，绝不做批量选择器。

## 四、五条点击纪律（批量写入正确性的全部来源）

这五条每一条都对应一次真实事故，缺一条就会产生错收。

### 4.1 只点目标行自己的按钮，禁止任何"兜底"

搜索结果列表里每一行都有自己的收藏按钮。当目标行尚未渲染出按钮时，如果代码写成"退而求其次，点页面上任意一个不属于列表项的按钮"，那个按钮极可能属于**上一轮搜索残留的详情面板**，也就是**另一家店**。

```js
// ✗ 错误写法：目标行按钮 || 页面上任意不在列表项内的按钮
const btn = inTargetRow || [...document.querySelectorAll('a.fav')].find(x => !x.closest('li'));

// ✓ 正确写法：只认目标 uid 对应那一行自己的按钮；找不到就不点，记失败待重试
const row = document.querySelector(`li a[href*="uid=${uid}"]`)?.closest('li');
const btn = row?.querySelector('a.fav');
if (!btn) { /* 记 no_btn，留给重试轮 */ }
```

### 4.2 候选列表首项可能不是门店

平台的候选列表里会混入**图片占位项**等非门店条目。跳过它、选中下一行**是正确的**，不要因为"点了第二条"就误判为 bug。

判据是**落库对象的 uid 与目标 uid 是否一致**，而不是"点的是第几行"。审计已收藏数据时同样按 uid/名称比对，不按位置推断。

### 4.3 列表项链接可能是"纠错反馈"而不是详情页

某些平台的列表项链接实际指向**反馈/纠错**页面，直接点击会弹出错误页标签，随着跑批越点越多，最终把浏览器内存吃光。

```js
// ✓ 点击前阻止默认行为（不开新标签），保留冒泡让列表打开详情面板
a.addEventListener('click', e => e.preventDefault(), { once: true });
a.click();
```

**判别信号**：如果你看到"每个视频/每条搜索都弹出一个报错标签页"，先怀疑这里，而不是账号被限。

### 4.4 收藏按钮的判定条件要同时看 title 与 class

```
未收藏：title="加入收藏夹"（按钮为空心态）
已收藏：title="取消收藏" 且 class 含已收藏标记
```

**成功判据必须是"按钮变为已收藏态"**，而不是"点击动作已发出"。

只搜索、不点收藏、不进详情页的"空转"必须被计数并在收尾时暴露出来 —— 否则会出现"脚本报告成功 300 条、账号实际只多了 30 条"的情况。**每次运行都要用"账号侧实际增量"对账，而不是相信脚本自报。**

### 4.5 危险操作永远不做批量选择器

```js
// ✗ 这行会取消页面上所有已收藏项，包括用户自己的历史收藏
document.querySelectorAll('a.fav.has-faved').forEach(x => x.click());
```

任何取消/删除动作都必须**按目标标识精确定位单条**。这条踩过一次，直接损失了用户的两条既有收藏（后经 UI 重新收藏恢复）。

## 五、名称匹配分级（准确率优先）

外部清单里的店名经过 OCR 与人工整理，与平台收录名天然存在差异。**"名字对不上也点收藏"是最大的质量杀手** —— 快速跑完全量却收进一堆错店，等于白跑。

| 规则 | 条件 | 处置 |
|---|---|---|
| R0 | 主名完全相同 | 自动收藏 |
| R1 | 目标名包含候选名（候选 ≥ 3 字，且非纯品类词） | 自动收藏 |
| R2 | 候选名包含目标名（目标 ≥ 3 字） | 自动收藏 |
| R3 | 修饰词 + 目标名（修饰词在白名单内且 ≤ 4 字） | 自动收藏 |
| — | 以上均不满足 | **不收藏**，进待人工清单 |

**主名归一化**：去括号分店后缀、去 `·` 等分隔符及其后内容、去话题标签、去首尾空白、转小写。

**两条硬约束：**

- **纯品类词黑名单**：`烧烤 / 煎饼 / 肉夹馍 / 卤面 / 汤包 / 面馆 / 小吃 / 快餐 …`。候选名若只剩目标名里的那个品类词，一律拒收 —— 防「某某记肉夹馍 → 肉夹馍」「某某特色烧烤 → 特色烧烤」这类误配。
- **连锁处理**：同一主名下的不同分店视为连锁；**每个品牌最多收 5 家分店**。连锁店全收会把收藏夹刷满、淹没真正想去的那家。

**改动匹配规则后必须做离线回归**：拿历史真实案例跑一遍，确认"该拦的拦住、该收的收到"，通过再上线。本项目落地的回归集为 15 条已知误配 + 12 条已知同店异写。

**待人工清单是要收尾的**：名称不符 / 疑似同店两类失败要落成结构化清单（城市 + 目标名 + 当时候选名），跑完后统一人工判断，而不是混在日志里丢掉。

## 六、几个必须踩过的坑

### 6.1 先删后写 = 数据丢失

最初的实现顺序是"先删除 → 再打开详情页 → 点收藏"。在约 20 秒/条的节奏下，单页应用会偶发初始化失败，结果是**点被删掉了但没被加回来**。

**修正：把顺序反过来 —— 先确认详情页可用，再执行删除。** 页面不可用就什么都不做，只记一条待重试。这样在结构上就不可能产生"删了加不回"。

### 6.2 把"查无此 POI"误判成限流

目标平台在找不到 POI 时，会返回一个固定的错误响应（响应体长度恒定、关键词字段被清空、业务 `code` 为固定值）。这**不是限流**。

真限流的表现是**请求挂起/超时**。两者必须分开处理：前者直接判定"平台无此 POI"，后者才退避重试。

曾经把前者当成后者做指数退避，最长空转了 1.5 小时。**诊断时空结果必须打印关键词、请求状态码、响应体长度和前 200 字符。**

同理：**轻量联想接口在连续调用后会被降级为返回空**。这也不是"这家店不存在"。判别方法是对同一关键词做对照请求，若"带全部参数/不带参数都返回空"且前面刚连续成功过，就是降级，应当暂停而不是继续跑。

### 6.3 强烈依赖带哈希的 CSS 类名

前端构建一变，写死的类名就全部失效，而且失败表现是"页面上找不到按钮"，很容易误判为账号被限。

**修正：改用 `[class*="前缀"]` 属性选择器 + 等待选择器出现 + 失败自动重新加载重试。**

### 6.4 别把"没抓完"当成"不匹配"

候选列表抓取轮询的退出条件如果写成"轮询 N 次后退出"，会在页面还没渲染出来时就判定"候选均不匹配"，造成**明明第一行就是正确的店却没点**。

**修正：区分"抓到候选但不匹配"与"根本没抓到候选"，后者记 `retry` 而不是 `no_match`。**

### 6.5 城市参数硬编码 = 整批全废

把"目标城市"这个参数写死成本地城市码，会让**所有非本地城市**的条目都在错误城市里检索，结果全部被判"无匹配"。表面上像是"这批外部清单里没有这些店"，实际是查错了地方。修复成查表之后，同一批条目一次就命中。

**纪律：城市/地区码必须查表；新增城市前先确认表里有，表里没有就必须先补表，不能让它静默回落到默认值。**

### 6.6 解析器少认一种标签，整段条目直接消失

外部清单文档里的条目可能被放在列表标签（`<li>`）里。如果解析器只把换行标签当作分隔符、不处理列表标签，整段会被合并成一行，然后因为"名称超长"被过滤掉。

**表现极具迷惑性：不是"跑失败了"，而是"这一段一条都没跑"，且失败清单里也看不到它们。**

**纪律：解析完必须做条目数对账（文档里有几条 vs 解析出几条），差值为 0 才允许进入执行阶段。** 本次就是靠这条对账发现有一整类城市的条目从未被识别过。

### 6.7 写操作不能"抓一次请求然后批量重放"

平台给写接口签了一个**在页面内生成的校验字段**。把一次真实的写请求原样复制出来、换个参数重放，会被服务端判定为非法访问（返回 `invalid access`）。

**结论：所有写操作只能由页面驱动，接口只用来读。** 这条在动手前就能判定，可以省掉一整轮"抓包 → 重放 → 全部失败"的试错。

## 七、浏览器自动化：跑得稳才有速度

### 7.1 连本地已登录浏览器，而不是云端虚拟浏览器

云端虚拟浏览器通常是软件渲染，地图类 SPA 的 POI 面板与收藏按钮**根本加载不出来**，还容易触发验证码。正确做法是连接**用户本机已登录的实体浏览器**的调试端口。

| 要点 | 说明 |
|---|---|
| 调试端口 | 启动时加 `--remote-debugging-port`，并配**独立 profile 目录**，与用户日常浏览器隔离 |
| 连接地址 | 用 `localhost` 而不是 `127.0.0.1`（部分环境只监听 IPv6，用字面量 IPv4 会连不上，表现为 `bind() returned an error`） |
| 进程管理 | **绝不使用"按进程名批量结束"**。只关闭本任务自己开的标签页；需要重启浏览器时按 profile 精准匹配。用错了会连带关掉用户正在使用的浏览器 |
| 登录态失效 | 遇到扫码/验证码立刻暂停并把页面交给用户，不尝试绕过 |

### 7.2 三条会让整批任务崩掉的实现细节

| 现象 | 根因 | 修正 |
|---|---|---|
| `spawn ... EBUSY` | Windows 下同步 spawn 同一个可执行文件被文件锁挡住 | 改为异步 spawn，一条一个独立进程 |
| `EPERM: xxx.tmp` | 结果文件被占用，写临时文件再改名失败 | 临时文件名带进程号 + 重试若干次 + 直接覆盖兜底 |
| `Attempted to use detached Frame` | SPA 换页后旧句柄失效 | 每步操作前检查句柄存活，失效就重开标签 |

### 7.3 架构：进程级故障隔离 + 自愈

长驻脚本依赖"由外部单独启动的浏览器"是脆的 —— 浏览器一被外部因素影响退出，整批就崩，而且失败发生在几十条之后才被发现。

```
常驻守护进程
 ├─ 探活调试端口 → 断了就自己拉起浏览器（独立 profile，不动用户浏览器）
 ├─ 每条任务开一个独立子进程 → 单条崩溃不影响全局
 ├─ 结果文件原子写入 → 随时可断点续跑
 └─ 进度看板文件按条刷新 → 外部随时可读，不需要问脚本
```

### 7.4 两段式取件 + 有上限的重试

失败要分两类，否则要么永远不重试、要么死循环：

| 类别 | 状态举例 | 处置 |
|---|---|---|
| **终态** | 已收藏 / 平台确实无此 POI / 名称不符 | 不再重跑，进失败清单 |
| **可重试** | 页面未渲染 / 脚本异常 / 按钮未出现 / 帧失效 | 最多重跑 N 次（建议 3），计数写入结果文件 |

取件顺序：**先把"从未处理过"的按原顺序跑完，全部跑完后才回头扫可重试项。**

这样既保证队列顺序，又不让重试项插队打乱节奏，也不会在一条反复失败的条目上空转。同时按唯一键去重落盘，避免重跑把结果文件撑大、状态统计失真。

## 八、抗限流：做成结构性能力，而不是调参数

目标平台的访问频率是有上限的。要长时间无人值守跑完，需要把"抗限流"做成结构性能力。

| 机制 | 作用 |
|---|---|
| **滑动窗口配额** | 1 小时内请求数硬上限，超出自动等待窗口滑出 |
| **最小请求间隔** | 任意两次请求之间强制间隔，并叠加小幅随机抖动，避免机械规律 |
| **批次休息** | 每 N 条休息若干秒，给单页应用留出内存回收窗口 |
| **两级熔断** | 接口连续失败 → 冷却 30 分钟；页面连续失败 → 冷却 10 分钟 |
| **探活恢复** | 冷却后先探测接口可用性，通过才继续；多次失败则安全退出而非硬刚 |
| **异常识别** | 状态码异常 / 返回非 JSON / 业务状态位异常 三类信号分别识别 |
| **失败补回队列** | 任何"已删除但未加回"的条目进入补回队列，收尾统一重试 |
| **断点续跑** | 每处理一条即落盘，按唯一标识去重，中断后可原地继续 |

**节奏参考：** 300 请求/小时 ≈ 120 条/小时。慢，但可以整夜无人值守。

**关键：** 配额、间隔、熔断与计数内嵌在**统一的请求网关**里，而不是散落在业务代码中。

**关于"请求数"的口径**：不要把页面加载产生的全部网络请求（瓦片、埋点、活动配置）都算进配额，那会把可用速率低估两个数量级；真正参与风控计数的是**业务接口调用**。反过来，也不要只数自己主动发的那一个接口而忽略详情页与写入。口径错了，速度和安全都会错。

## 十、参考实现骨架

以下为流程骨架，用于说明顺序与状态机，不是可直接运行的成品。

```

for 每一条待处理条目:

    若超时 → 重新加载最多 3 次
    若仍失败 → 记录 page_unavailable，跳过（不删除任何东西）

    # 阶段二：确认页面可用后才写
    按 uid 精确定位目标行自己的按钮

收尾：对可重试类失败统一补跑；对名称不符类失败输出人工清单
```

**候选匹配伪代码：**

```
function 匹配(目标名, 候选名):
    主名 = 去括号分店后缀 / 去分隔符后缀 / 去话题标签 → 小写
    if 主名完全相同                              → 自动收藏 (R0)
```

## 十一、收藏夹分组（标签）：容量上限与有损写入

收藏夹的"分组"是另一类写操作，和"收藏/取消收藏"完全不同的一套约束。把收藏按地理或主题归类时，先看清下面三件事，否则会在中途卡死。

### 11.1 平台把组织关系放在三个平行通道里

| 通道 | 归属 | 能否自建 | 说明 |
|---|---|---|---|
| 地区分组 | 平台自动 | 否 | 收藏时按 POI 所属城市自动归组；实测账号有 130+ 个城市组 |
| 品类分组 | 平台自动 | 否 | 按 POI 品类（餐饮 / 购物 / 景点 …）自动归组 |
| **自定义分组** | 用户 | **是** | 唯一可自建的通道，也是"按省 / 按大区分组"这类需求的实际载体 |

**推论：如果需求是"按城市分组"，多数平台已经自动做好了，不需要自建。** 先确认这一点，能省掉一整轮无用功——本次就是在准备动手前才发现的。

### 11.2 三条硬约束（都来自实测）

**约束一：自定义分组有硬上限。**

达到上限后再建组，服务端返回一个业务错误码（实测形态：`{"type":8000,"error":7}`），**前端不弹任何提示、界面无任何变化**——只表现为"新建按钮点不动"。

批量建组时必须**逐个回读校验**（建一个、拉一次分组清单、确认新组在里面），不能相信"点击动作已发出"。本次就是靠回读发现"从第 21 个开始全部静默失败"，否则会一路空跑下去。

**约束二：一条收藏只能挂 1 个自定义分组，新分组覆盖旧分组。**

平台在弹窗里写得很直白：新分组会覆盖之前添加过的分组。这意味着"打分组"是一次**有损写操作**：

- 动手前先导出"每条收藏当前挂在哪个分组"作为备份；
- 或者明确接受覆盖，并在动手前告诉需求方"会覆盖掉哪些、涉及多少条"。

本次涉及的旧分组里，有一个占用了几百条，其余几个是空组——**先统计"每个分组实际挂了多少条"，能准确判断哪些删掉是零损失的**，这个统计只要一次全量读就能做。

**约束三：网页端没有删除 / 重命名分组的入口。**

分组弹窗与筛选菜单里都没有删除控件，入口只在移动端 App。因此**分组规划必须在动手前定稿**：先建错、再想改，就得回到手机上去删。

### 11.3 建组的实现细节

- 新建分组的输入框**默认带 `disabled`**，直接向它输入内容打不进字（表现为"输入后仍然为空、点击添加无反应"）。需要先解除 `disabled` 再输入，然后再点"添加"。
- 建完后回到分组清单复核，确认新组确实出现（见约束一的回读要求）。
- 删除没有任何前端入口，不要在这一步上耗时间。

### 11.4 批量贴分组：先筛后贴，不要逐条贴

正确顺序是**按地区筛选 → 逐页多选 → 批量贴该地区对应的分组**：

```
选定地区分组（作为筛选条件）
        ↓
逐页全选本页条目
        ↓
一次性贴同一个目标分组
        ↓
回读校验本页条目已带上该分组
```

逐条打开弹窗贴分组在数千条规模上是**小时级**耗时，而且每条都要开一次弹窗，失败率会随运行时长上升（弹窗句柄失效、列表刷新、帧重载）。本项目的量级参考：数千条、数百页，按"先筛后贴"的方式压在 1–2 小时内跑完。

### 11.5 容量规划：先算分布，再定名单

上限只有 20 个，而全国省级行政区有 30 多个——**照抄行政区划必然装不下**。

正确的顺序是：

1. **先算分布**：每一条收藏属于哪个地区，得到"地区 → 点位数"的排序表；
2. **再定名单**：按点位数从高到低取前 N，把几乎没点位的组腾出来换给大头；
3. **最后动手**：建组、贴组、回读校验。

本次实测的分布是高度长尾的：最大的一个地区占近三成，前 20 个地区覆盖约 95% 的点位，尾部十几个省份合起来只有个位数。**如果按行政区划硬建，会出现"占着位置的省只有 1 条，而最大的省没位置"这种荒谬结果。**

### 11.6 与"收藏 / 撤销"的一致性

三条纪律在这里同样适用：**按标识精确定位、一次只改一条（或一页）、每次都回读校验**。分组写入失败往往没有任何报错，唯一可靠的判据是**回读分组清单**，而不是点击是否发出。

## 十二、清单解析：一份文档里可能有三种写法

批量写入的分母是一份外部清单（常由他人整理成长文档）。**解析器少认一种标签，整段条目直接消失**——不报错，只让统计数字悄悄变小。

| 写法 | 形态 | 解析要点 |
|---|---|---|
| 段落 + 换行 | `<p>甲<br/>乙<br/>丙</p>` | **必须按换行标签拆分**，否则整段被当作"一个超长名字"被噪声过滤丢掉 |
| 列表 | `<ul><li>甲</li></ul>` | 逐条取 `li`；条目里可能嵌删除线 + `→` 修正名，**要取箭头后的名字** |
| 表格 | `<table><td>店名</td>` | **按表头文本定位"店名"列**，不可写死列号 |

**按标题切段的两个坐标陷阱**：起点必须取标题标签**结束位置**，终点取**下一个同级标题的起始位置**。起点取错 → 切出空段（条目为 0）；终点取错 → 段尾吞掉整篇（条目暴涨几十倍）。

**标题标称数 ≠ 段落条目数，且三种情形都正常**：标称 > 实际（标称是"该城市所有来源汇总"，段落只列单来源）；标称 < 实际（标称是早前统计，之后又追加了条目）；标称 == 实际（单来源城市）。**核对数量前先对齐口径，不要在口径没对齐时报"数据错了"。**

## 十三、增量对账：自报"成功"不可信

执行器每条都回读了按钮状态、都判"成功"，但账号真实增量明显更少。**实测：自报 169 条 → 按记录标识对账只有 132 条，假成功约 22%。**

唯一可靠的判据只有一个式子：

```
真实增量 = 快照B.标识集合 － 快照A.标识集合
```

用**记录标识**做差，不要用名字（平台改名/别名会对不上）。**没有这个差集，"跑了 N 条成功"都不算数。**

反方向也会错——**假阴性**：目标名与平台收录名有细微差异时（字序颠倒、多一个品类后缀），条目其实早已收藏，却被判成"未收藏"。修正办法是加一级**宽松匹配复核**（完全相同 → 收录名包含目标名 → 目标名包含收录名 → 前 2 字相同 → 相似度 ≥0.7）。**纪律：宽松匹配的结果必须人工过一遍**，否则会把"区域名/品类词"误配进来，完成度虚报十几个百分点。

**被严格规则误杀的条目，重跑一轮通常就能收进去**（实测 18 条成功 14 条，77.8%），不需要改数据、也不需要放宽全局规则，只需对这一小批启用"指定候选词"的精确模式。

## 十四、视频平台清单抓取（以 B 站空间页为例）

| 卡点 | 现象 | 修正 |
|---|---|---|
| 登录墙 | 未登录时数据接口返回风控码，旧接口直接返回 HTML | 打开登录页截二维码给用户；**扫码成功后先验证登录态**，不要重复让用户扫 |
| 分页 ≠ 无限滚动 | 滚动到底只加载首屏，页高不再变化 | 找分页控件，逐页点"下一页"直到按钮 disabled；页面计数文本会给出"共 N 页 / 共 M 个" |
| 标题不在常规位置 | 常规标题选择器取到的是播放量等噪声 | 标题在封面图片的 `alt` 属性里；**先 dump 一张卡片的完整 HTML** 再写选择器 |

**量级换算：视频数 ≠ 门店数。** 实测某创作者 536 个视频，只能从标题抽出约 360 家门店（**折算率约 0.7**）：

| 标题类型 | 占比 | 能否提取 |
|---|---|---|
| `区域｜店名` 格式 | ~74% | ✅ 直接提取 |
| 榜单 / 合集（"某地必吃餐厅 2026 版"） | ~10% | ❌ 店名在视频正文 |
| 纯叙述 | ~13% | ❌ 无锚点 |
| 正文里嵌了店名 | ~4% | ⚠️ 需人工补提取 |

**不要把"视频数 = 门店数"写进承诺。** 要更高必须逐条进视频页读简介，风控暴露面显著上升。

## 十五、环境漂移：脚本里别写死运行时路径

**实测故障**：运行时目录名带补丁号（`.../22.22.2-5/`），一次升级后变成 `.../22.22.2-6/`，**所有写死该路径的脚本一次性全部失效**。

- 脚本内用变量集中定义运行时路径，或在启动脚本里用环境变量注入；
- 升级前先 `grep` 出所有硬编码引用，逐条确认再批量替换；
- 每次开跑前先探活（调试端口 / 运行时版本），失败即停并给出明确原因。

## 十六、适用边界

**适用：**

- 需要把收藏从平台 A 迁移到平台 B，且要求落点与平台 B 自己的门店点位一致
- 需要按外部清单（含 OCR 整理的店名）在平台上批量写入收藏
- 平台上存在"接口写入"和"页面按钮写入"两条路径，且两者结果不同
- 需要长时间无人值守跑完大批量写入

**不适用 / 需要额外处理：**

- 目标平台对收藏总量有硬上限。达到上限后继续写入会挤出最早的数据，**且接口返回的总数不会变化** —— 计数无法用来判断真实容量，必须依赖客户端界面确认。
- 纯行政区划名称（县、市、区）通过 POI 检索接口通常查不到，需要在地图上人工处理。
- 大型景区、山脉、湖泊等面状地理实体，其在两个平台的代表点天然相差数公里，不适用"偏移"判定，应按平台自身点位处理。
- 名称经 OCR 整理后与平台收录名差异过大的条目，机器无法可靠判定，必须留给人工。
- **自定义分组有硬上限且不报错**（见第十一节）：需求按 30+ 个行政区划建组时，必须先算点位数分布再取前 N，且"建组失败"没有前端提示，只能逐个回读校验。
- **一条收藏只能挂 1 个自定义分组**：分组归类是有损写操作，动手前要么备份原有归属，要么明确告知需求方覆盖范围。
- **网页端没有分组删除入口**（多数平台只在移动端）：分组名单必须在动手前定稿。
- **外部清单往往是"多格式混排"的长文档**：解析器必须同时支持段落换行 / 列表 / 表格三种写法，并把"每城条目数"与"标题标称数"做对账（见第十二节）。
- **完成度统计必须用记录标识做集合差**：执行器自报会虚高（实测约 20%+）；"未收藏"判定也会假阴性——名称有细微差异时条目其实早已收过（见第十三节）。
- **"视频数 = 门店数"不成立**：实测折算率约 0.7，榜单 / 叙述类视频的标题里没有店名（见第十四节）。
- **不要把运行时版本路径写死在脚本里**：目录名带补丁号，一次升级会让整批脚本失效（见第十五节）。

## 十八、脱敏说明

- 不包含任何真实店铺名称、门店标识、经纬度坐标
- 不包含任何账号信息、会话凭据、平台令牌、Cookie
- 不包含本地文件路径、运行日志、原始数据快照
- 涉及具体数值的部分只保留量级与相对关系（如"约 95 m""4 套坐标""约 7 秒/条"），不保留可直接定位到个体的信息

## 十九、文档与封面

本仓库的 README 结构参考了 [dingshuxin353/readme-skill](https://github.com/dingshuxin353/readme-skill) 的"证据优先"写法：先把仓库事实分级（已验证 / 用户提供 / 推断 / 未知），没有依据的内容不写进文档。

封面参考了 [JennieWei/jennie-dingding-cover-packager](https://github.com/JennieWei/jennie-dingding-cover-packager) 的封面系统：单一标题承诺、清晰的视觉层级、背景不空也不乱。封面以矢量方式绘制后导出，以保证中文标题的精确呈现。
